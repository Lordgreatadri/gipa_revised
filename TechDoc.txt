This technical documentation is designed to be handed directly to a development team to build TheLeads Laundry Management System (TLMS) as a multi-tenant SaaS / Platform-as-a-Service (PaaS) product. It assumes that TheLeads Laundry & Dry Cleaning will be one of many laundry businesses using the platform, even though you own the platform itself.

### TheLeads Laundry Management System (TLMS) — Technical Documentation

### 1. Project overview

Project name: TheLeads Laundry Management System (TLMS)

Product type: Multi-tenant SaaS / Platform-as-a-Service for laundry and dry-cleaning businesses.

Primary goal: Enable independent laundry businesses to register, subscribe, and manage their daily operations — including customers, orders, pickups, deliveries, payments, staff, notifications, and loyalty programs — from a centralized cloud platform.

### Core business model

* Platform Owner (Super Admin): Manages the SaaS platform, subscriptions, pricing plans, support, and global settings.

* Laundry Tenant: Each laundry business signs up as an independent tenant with isolated data.

* Tenant Staff: Employees of a laundry business manage operations based on assigned roles and permissions.

* End Customers: Customers of each laundry business receive services, notifications, and loyalty rewards.

### Multi-tenancy strategy

Use single database, shared schema with a `tenant_id` column on all tenant-owned tables.

* Pros: Lower infrastructure cost, easier maintenance, simpler backups.

* Cons: Requires strict query scoping to prevent data leakage.

* Recommendation: Use stancl/tenancy or a custom Laravel global scope for tenant isolation.

* Event dispatches a queued job.

* Redis stores the job.

* Delivery status is logged in `sms_logs`.

### 5.6 Loyalty and rewards system (This should be optional, configurable by each tenant)

### Business requirement

A customer who collects and presents 5 receipts receives the 6th service free (or a configurable discount).

### Recommended implementation

Use a points-based loyalty system rather than physical receipt counting with SMS to notify customer of winning acceptable point for a free service.

### Logic flow

* Each completed order earns 1 loyalty point.

* When points reach 5 (configurable by tenant), customer becomes eligible for a reward.

* System generates a reward voucher and SMS to the customer.

* Voucher can be redeemed on the next order.

* After redemption, points reset or continue accumulating based on tenant settings.

### Loyalty tables

* `loyalty_programs`

* `loyalty_points`

* `reward_vouchers`

### Reward configuration

| Setting          | Example       |
| ---------------- | ------------- |
| Points per order | 1             |
| Points required  | 5, 10, 15 etc |
| Reward type      | Free service  |
| Reward value     | 100% discount |

### 9. Security considerations

* Tenant isolation: Every query must be scoped by `tenant_id`.

* Authentication: Use Laravel Sanctum for API authentication.

* Authorization: Use Spatie roles and permissions. With tables defined and seeded

* Data encryption: Encrypt sensitive customer data where necessary.

* Audit logs: Record all critical actions.

* Backups: Daily automated database backups.

* Rate limiting: Prevent abuse of SMS and API endpoints.

### 14. Key business logic rules

* Receipt numbers: Must be unique per tenant (e.g., TL-2026-0001).

* Order status: Cannot skip mandatory workflow steps unless overridden by a manager.

* SMS credits: Tenants cannot send bulk SMS without sufficient credits.

* Loyalty rewards: Points are awarded only after payment is completed.

* Subscription expiry: Tenant access is restricted when subscription expires.

* Data deletion: Use soft deletes for auditability.

### 15. Final recommendation

For TheLeads Laundry Management System, I strongly recommend building the first version as a Laravel 11 multi-tenant SaaS platform using Blade, Tailwind CSS, MySQL 8, Redis, and Spatie Laravel Permission. This approach is cost-effective, fast to develop, and scalable enough to support hundreds of laundry businesses before needing to migrate to a more complex microservice architecture.

The teal-and-white color palette (#0F766E, #14B8A6, and #F59E0B) will give the platform a modern, trustworthy, and premium appearance while remaining bright and mobile-friendly.

This document provides the functional requirements, architecture, database design, workflows, security rules, and development roadmap needed for a developer or development team to begin building the system immediately.
